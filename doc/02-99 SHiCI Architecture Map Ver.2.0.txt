SHiCI Architecture Map
Version 2.0


------


1. Purpose（目的）

SHiCI Architecture Mapは、SHiCIの設計思想、Processing Model、および実装コードの対応関係を定義する文書である。

本書の目的は、設計上の概念が、どのコードによって実現されるのかを明確にし、設計と実装の一貫性を維持することである。

Architecture Mapは、個別機能の詳細仕様を定義する文書ではない。

また、アルゴリズム、データ項目、画面デザイン、Promptの具体的内容を定義する文書でもない。

Architecture Mapは、

設計思想と実装責務を結び付ける地図

である。


------



2. Position in Design Hierarchy（設計階層上の位置）

SHiCIの設計文書は、次の階層を持つ。

00 SHiCI Charter
        ↓
01 SHiCI Constitution
        ↓
02 SHiCI Core Design
        ↓
各Domain Model
        ├─ Processing Model
        ├─ Understanding Model
        ├─ Conversation State Model
        ├─ Entity Resolution Model
        ├─ Knowledge Boundary Model
        ├─ View Specification Model
        └─ Response Specification
        ↓
SHiCI Architecture Map
        ↓
Source Code

上位文書ほど、長期間維持される原則を定義する。

下位文書ほど、具体的な実装との対応を定義する。

Architecture Mapは、上位の設計書を置き換えない。

Architecture Mapは、それらの設計をコードへ対応付ける。

3. Fundamental Architecture（基本構造）

SHiCIの処理は、Processing Modelに基づき、次の六段階で構成される。

Input
  ↓
Understand
  ↓
Resolve
  ↓
Compose
  ↓
Express
  ↓
Output

ただし、これはEngineの実行順をそのまま示すものではない。

Knowledge BoundaryやView Resolutionなどは、各Processing段階の内部で行われる。

Conversation Stateは独立した処理段階ではなく、会話の継続性を保持する横断的な状態基盤である。

5. Cross-Cutting State（横断的状態基盤）
Conversation State

実装：

21_ConversationStateEngine.js

Conversation Stateは、Processing Model上の独立した段階ではない。

会話をまたいで必要となる状態を保持し、UnderstandおよびResolveを支援する。

保持対象の例：

currentEntity
candidateEntities
currentView
conversation history

Conversation Stateは、次の場面で利用される。

Understand
    ├─ 現在のEntityを参照する
    ├─ 現在のViewを参照する
    └─ 直前の候補選択を解釈する

Resolve
    ├─ 候補一覧を保存する
    ├─ 選択されたEntityを確定する
    └─ 曖昧性を次の発話へ引き継ぐ

Conversation State自身が、Entityを探索したり回答を生成したりしてはならない。

6.2 Understand

責務
ユーザーが何を伝えようとしているかを理解する。

主実装
17_UnderstandingRequestContract.js
18_UnderstandingResultContract.js
20_UnderstandingEngine.js
70_LLMInterface.js

補助実装
19_CommunicationEngine.js
21_ConversationStateEngine.js
23_ViewResolutionEngine.js
25_KnowledgeBoundaryEngine.js
26_GeneralKnowledgeEngine.js
28_UpdateUnderstandingAdapter.js

28_UpdateUnderstandingAdapter.jsは、
Understandingを行うEngineではない。

Understanding Resultに含まれるCanonicalなUpdate情報を、
現在のUpdate処理が利用できる内部形式へ変換する互換Adapterである。



Understand内部の判断
User Input
    ↓
Understanding Request Contract
    ↓
LLM Interface
    ↓
Provider Adapter
    ↓
Understanding Result Contract
    ↓
Intent / Entity Query / Change / Missing Fields
    ↓
Knowledge Boundary Selection
    ├─ Communication
    ├─ Company Knowledge
    ├─ General Knowledge
    ├─ Derived Knowledge
    └─ Unknown

Version 2.0では、すべてのユーザー入力は、
まずUnderstanding Request Contractとして構造化される。

LLMは自然言語の意味をUnderstanding Resultへ変換する。

Understandingは、次を行わない。

・Knowledge検索
・Canonical Entity確定
・Snapshot生成
・業務上の妥当性判断
・権限判断
・更新案生成
・データ更新

現在、Understanding Resultを正式に利用している処理は、
金型温度Update経路である。

質問、Communication、General Knowledge等の非Update経路では、
Understanding Result生成後も、一部の経路選択に既存Engineの判定を使用している。

非Update経路も段階的にUnderstanding Result中心へ移行する。

Understandが決定してよいこと
発話がCommunicationか
どのKnowledge Boundaryを必要とするか
どのViewを求めているか
既存のConversation Contextを利用するか
Entity Resolutionが必要か

Understandが決定してはならないこと
Canonical Entityの最終確定
Snapshotの構築
業務上の回答内容
一般知識による事実補完

Resolveは、Snapshotを構築してはならない。

Resolveは、業務回答を生成してはならない。

Resolveは、一般知識を使って存在しないEntityを生成してはならない。

7. Knowledge Boundary Mapping

Knowledge Boundaryは、独立したProcessing段階ではない。

Understand段階において、今後どのKnowledge経路を利用するかを決定するための分類である。

実装：

25_KnowledgeBoundaryEngine.js

--

7.1 Communication
実装
19_CommunicationEngine.js
経路
User Input
    ↓
Understanding Engine
    ↓
Knowledge Boundary = communication
    ↓
Communication Engine
    ↓
AI Contract
    ↓
LLM Interface
    ↓
Adapter
    ↓
Response
特徴
Entity Resolutionを行わない
Snapshotを構築しない
社内Knowledgeを渡さない
業務上の事実を生成しない
自然な会話を許可する

Communicationも、正式なAI Contract経路を使用する。

Communication専用のOpenAI API経路は作らない。

--

7.2 Knowledge
経路
Understand
    ↓
Resolve
    ↓
Compose
    ↓
Knowledge用AI Contract
    ↓
Express
根拠

SHiCI内部に登録されたKnowledgeのみ。

原則
Contextにない事実を補わない
登録がなければ登録されていないと答える
内部構造名をユーザーへ露出しない

--

7.3 Derived Knowledge
経路
Knowledge
    ↓
再現可能な計算・導出
    ↓
Derived Knowledge
原則
元データを明確にする
計算式を再現可能にする
一般値や推定値を無断で混ぜない

Derived Knowledgeは、Knowledgeを根拠とする。

--

7.4 General Knowledge
経路
Understand
    ↓
General Knowledge Contract
    ↓
LLM Interface
    ↓
Adapter
原則
社内Knowledgeと区別する
「一般的には」など、根拠の立場を明示する
社内仕様として断定しない

Version 2.0では、
26_GeneralKnowledgeEngine.jsによる初期経路が実装されている。

ただし、Knowledge Boundaryの判定は、
まだUnderstanding Resultの構造化情報へ完全には統合されていない。

--

7.5 Unknown
対象
必要な社内情報が存在しない
一般知識でも安全に回答できない
質問の意味を特定できない
根拠が不足している
原則
推測で埋めない
架空のEntityを生成しない
内部用語を表示しない
必要に応じて追加情報を求める

Version 2.0では、
Knowledge Resolution失敗時のユーザー向け表現を改善する必要がある。

将来的には、
Unknown Response Contractに基づく自然な応答へ統一する。

12. Known Architectural Gaps（現在認識されている差異）

Architecture Map Version 2.0更新時点で、次の差異が存在する。

--

12.1 Understanding Engineの責務が広い

現在のUnderstandingEngine_handle()は、

Understand
Resolveの制御
Composeの起動
Expressの起動
最終回答の返却

まで担当している。

Processing Model上では、Understandingは入力理解のみを担当すべきである。

将来的には、Application OrchestratorまたはConversation Engineへ、処理全体の統括責務を分離する余地がある。

ただし、Version 2.0でも直ちに分割しない。

現在の優先事項は、
非Update経路をUnderstanding Result中心へ段階的に移行することであり、
Orchestratorの分離そのものではない。

--

12.2 AnswerBuilderが残存している

50_AnswerBuilder.jsは、LLM以前の固定形式回答を生成する旧Express実装である。

現在も候補選択直後など、一部経路で利用されている。

将来的には、

View Specification
Response Specification
Component Output

へ移行し、AnswerBuilderへの依存を段階的に削減する。

--

12.3 内部構造名がユーザーへ露出する

現在、Entity候補が見つからない場合に、

現在のEntity Resolution Knowledgeでは、
該当する候補が見つかりませんでした。

と返している。

これは内部構造の露出であり、SHiCIの会話原則に反する。

将来的には、Unknown Boundaryに基づく自然な回答へ置き換える。

例：

その名前に一致する登録情報は見つかりませんでした。
別の呼び方や図番が分かれば教えてください。

--

12.4 UnknownおよびDerived Knowledgeが未正式化

General Knowledge経路は、
26_GeneralKnowledgeEngine.jsによって実装されている。

ただし、現在のGeneral Knowledge判定は、
自然言語の正規表現を中心とした初期実装であり、
Understanding ResultのKnowledge SourceまたはBoundary情報とは
まだ統合されていない。

Unknownは、独立したContractおよびEngineとして未正式化である。

現在は各処理経路が個別のエラー文または情報不足文を返している。

Derived Knowledgeも、
Knowledge Transformationとして設計上定義されているが、
統一されたContractおよび実行経路は未正式化である。

--

12.5 一部の責務がファイル間で混在している

現状では、LLMInterface_接頭辞を持つ処理がAdapter側へ置かれている箇所など、責務境界が完全には統一されていない。

原則として、

LLMInterface_* → 70_LLMInterface.js
OpenAIAdapter_* → 71_OpenAIAdapter.js
MockAdapter_* → 72_MockAdapter.js

へ整理する。


--


12.6 非Update経路がUnderstanding Resultを十分に利用していない

Version 2.0では、
すべての入力に対してUnderstanding Resultが生成される。

しかし、Update以外の処理では、
Knowledge Boundary、
View、
Entity Queryの一部を、
従来の正規表現または文字列加工によって再判定している。

そのため、

自然言語
    ↓
Understanding Result
    ↓
後続処理

というUnderstanding Modelの理想経路は、
Update処理では成立しているが、
質問系処理では完全には成立していない。

今後は既存機能を壊さない単位で、

・Knowledge Boundary
・View
・Entity Query
・Conversation Context利用

をUnderstanding Resultから後続処理へ引き渡す。

ただし、
一度に既存処理を全面置換してはならない。


--


12.7 旧UpdateIntentEngineが残存している

27_UpdateIntentEngine.jsは、
正規表現によって金型温度Updateを理解する旧実装である。

現在の本番Update入口では使用されていない。

ただし、新しいUnderstanding経路の安定確認と
参照箇所の完全確認が終わるまでは削除しない。

削除する場合は、
Architecture Map、
テスト、
参照関係を同時に更新する。




------




13. Refactoring Policy（リファクタリング方針）

リファクタリングは、一度に全体を作り直さない。

次の優先順位で行う。

1. ユーザーへ内部構造を露出しない
2. 回答根拠のBoundaryを守る
3. 既存機能を壊さない
4. Contract経路を統一する
5. 重複責務を整理する
6. Processing Modelとの一致を高める

設計上の理想だけを理由に、動作中のコードを大規模に変更してはならない。

各変更は、独立して検証可能な単位で行う。


------



14. Architecture Change Rules

新しいEngine、Contract、Adapter、Knowledge Boundary、Viewを追加した場合は、Architecture Mapを更新する。

次の変更を行う場合も更新する。

Engineの責務変更
処理経路の変更
依存関係の変更
Contract形式の変更
Legacy実装の廃止
新しいInputまたはOutputの追加
新しい外部Providerの追加

コードだけを変更し、Architecture Mapを更新しない状態を放置してはならない。


------



15. Architectural Principles

--

Principle 1

SHiCIは、機能ではなく構造から設計する。

--

Principle 2

Entity Resolutionより先に、発話の意味とKnowledge Boundaryを理解する。

--

Principle 3

KnowledgeはComposeで構築し、Expressで表現する。

--

Principle 4

Knowledgeと表現を混同しない。

--

Principle 5

Conversation Stateは、会話の連続性を保持するが、業務判断を行わない。

--

Principle 6

LLMは、Knowledgeを所有しない。

LLMは、Contractに従ってKnowledgeを表現する。

--

Principle 7

Adapterは、Provider固有の技術差だけを吸収する。

--

Principle 8

内部構造は、ユーザーへ露出しない。

--

Principle 9

登録されたKnowledge、導出されたKnowledge、一般知識、Communication、Unknownを区別する。

--

Principle 10

知らないことを、推測によって知っているように表現しない。



------



Conclusion

SHiCI Architecture Mapは、SHiCIの思想、Processing Model、各Domain Model、およびSource Codeを結び付ける文書である。

SHiCIの基本処理は、

Input
  ↓
Understand
  ↓
Resolve
  ↓
Compose
  ↓
Express
  ↓
Output

によって構成される。

Knowledge BoundaryはUnderstandの内部で回答根拠を決定し、Conversation Stateは会話全体を横断して継続性を保持する。

Entity Resolutionは対象を特定し、Snapshot EngineはKnowledgeを構築する。

Response SpecificationはKnowledgeをAI Contractへ変換し、LLM InterfaceとAdapterは、そのContractを外部AIによって表現する。

SHiCIにおいて、AIは事実を作る存在ではない。

SHiCIが構築したKnowledgeを、定められたBoundaryの中で、人間へ届ける存在である。



------



16. Evolution Principle（進化原則）

SHiCIは、最初から完全な構造を実装することを目的としない。

Architecture Mapは、SHiCIが最終的に目指す構造を示すものであり、実装は段階的にそこへ近づいていく。

したがって、開発途中では、一時的に責務が一つのEngineへ集約されることを許容する。

例：

UnderstandingEngine

    ・Knowledge Boundary
    ・Conversation State
    ・View Resolution
    ・Entity Resolutionの制御

これらが一つのEngine内に存在していても、それだけを理由に分割を行わない。

責務分割そのものは目的ではない。

目的は、

保守性・理解しやすさ・拡張性を高めることである。

そのため、次の優先順位を守る。

① 正しく動作する

↓

② 設計思想と一致する

↓

③ 機能を完成させる

↓

④ 重複責務を整理する

↓

⑤ Engineを分離する

機能追加中は、新しい機能をArchitecture Mapで定義された責務へ追加する。

一方で、途中段階で過度なリファクタリングは行わない。

Refactoring Trigger（リファクタリング開始条件）

次のいずれかを満たしたとき、責務分割を検討する。

Rule 1

一つのEngineが複数の独立した責務を持ち、理解が難しくなったとき。

Rule 2

同じ処理が複数のEngineへ重複し始めたとき。

Rule 3

新しい機能追加よりも、保守性向上の効果が大きくなったとき。

Rule 4

Architecture Mapとの乖離が大きくなったとき。

Premature Refactoring（早すぎるリファクタリングの禁止）

次の理由だけでEngineを分離してはならない。

ファイルが長くなった。
Engine名が気に入らない。
将来使うかもしれない。
「きれいな設計」に見える。

リファクタリングは、実際の責務が明確になった後に行う。

Evolution Policy（進化方針）

SHiCIは、

Idea
    ↓
Prototype
    ↓
Working System
    ↓
Architecture Alignment
    ↓
Optimization

という順序で成長する。

設計は実装を導く。

しかし、実装によって得られた知見は、設計へ必ず還元する。

Architecture Mapは固定された仕様書ではない。

SHiCIの成長に合わせて更新され続ける設計図である。
